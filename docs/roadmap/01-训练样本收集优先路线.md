# 训练样本收集优先路线

## 背景判断

当前阶段暂缓实现模型重训。真实样本量还不足，直接做重训很难稳定体现效果，也容易把主要精力消耗在流程完整性而不是模型可验证性上。

训练样本收集的架构设计已沉淀到 `docs/architecture/04-训练样本事件采集架构设计.md`。本 roadmap 只记录后续建设顺序和待办边界。

## 建设顺序

1. 事件采集基础设施
   - 建立 `ml_feedback_event` 事件表。
   - 建立后端事件写入服务。
   - 统一生成 `before_snapshot_json`、`after_snapshot_json`、`context_snapshot_json`。

2. 核心事件接入
   - 方案确认时写入 `SCHEME_CONFIRMED`。
   - 片段移动时写入 `ITEM_MOVED`。
   - 片段标注时写入 `ITEM_MARKED_GOOD` / `ITEM_MARKED_BAD`。

3. 事件看板
   - 展示方案确认事件量、片段调整事件量、人工标注事件量。
   - 展示教师、班级、课程覆盖情况。
   - 区分真实确认样本和测试调整样本。

4. 样本构建器
   - 从 `ml_feedback_event` 读取事件。
   - 对 `ITEM_MOVED` 做 10 分钟调整会话压缩。
   - 对回到原位的调整会话做相消。
   - 按“人工标注 > 确认方案 > 调整行为”的优先级解释标签和权重。
   - 输出训练 CSV。

5. 样本质量检查
   - 检查正负样本比例。
   - 检查教师、班级、课程覆盖面。
   - 检查真实确认事件和测试调整事件比例。
   - 检查人工标注数量和原因分布。

6. 重训准备
   - 在样本量和覆盖面达到门槛前，不进入自动重训。
   - 达到门槛后，再设计固定验证集、评估指标和模型发布规则。

## 后续进入重训的条件

- 有足够数量的真实确认方案和手动调整记录。
- 有一定数量的人工好/坏标注。
- 正负样本比例不极端失衡。
- 教师、班级、课程覆盖面能够支撑对比评估。
- 能用固定验证集观察到模型排序或片段推荐质量变化。

在这些条件满足前，模型训练模块以事件采集、事件查询、样本质量检查为主。

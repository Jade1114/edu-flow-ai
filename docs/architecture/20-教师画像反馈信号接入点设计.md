# 教师画像反馈信号接入点设计

> 来源：`docs/architecture/19-毕设最终系统架构设计.md` 与 `docs/roadmap/03-毕设最终系统剩余开发清单.md`。
> 本文档记录现有“方案选择、人工调整、调课申请、人工标注”链路，并明确下一步如何把这些反馈事件聚合进教师画像。

---

## 1. 结论

当前项目并不是从零开始做反馈闭环。系统里已经有一套可复用的反馈事件基础设施：

- `ml_feedback_event`：反馈事件台账。
- `allocation_scheme_feedback`：方案确认级反馈。
- `allocation_item_adjustment_log`：排课片段人工调整日志。
- `adjustment_request`：正式课表调课申请。
- `/api/ml/feedback/export`：反馈数据导出。
- `/api/ml/feedback/train`：反馈训练入口。

现阶段真正缺口是：

```text
已有反馈事件 / 调整日志 / 调课申请
  → 尚未聚合为教师画像证据
  → 尚未影响 V3 final_profile
  → 尚未在教师画像页展示来源与置信度
```

因此 Phase 2 不建议新建一套 `teacher_profile_feedback_event` 表，而是优先复用 `ml_feedback_event`，在必要时补充事件类型和 snapshot 字段。

## 2. 已有数据表

### 2.1 `ml_feedback_event`

位置：`db/schema.sql`

用途：统一记录可进入模型训练或画像演进的反馈事件。

关键字段：

| 字段 | 说明 |
|---|---|
| `event_type` | 事件类型，如 `SCHEME_CONFIRMED`、`ITEM_MOVED`、`ITEM_MARKED_GOOD`、`ITEM_MARKED_BAD` |
| `task_id` | 分课任务 ID |
| `scheme_id` | 分课方案 ID |
| `item_id` | 分课明细 ID，可为空 |
| `teaching_task_id` | 教学任务 ID，可用于反查教师 |
| `reason_code` | 结构化原因 |
| `reason_text` | 人工原因或说明 |
| `before_snapshot_json` | 调整前快照 |
| `after_snapshot_json` | 调整后快照 |
| `context_snapshot_json` | 方案、来源等上下文 |

当前已支持事件类型：

```text
SCHEME_CONFIRMED
ITEM_MOVED
ITEM_MARKED_GOOD
ITEM_MARKED_BAD
```

### 2.2 `allocation_scheme_feedback`

用途：记录方案确认级反馈。

现状：方案确认时写入 `feedback_type = CONFIRMED`，并统计该方案调整次数。

### 2.3 `allocation_item_adjustment_log`

用途：记录教务在候选方案中手动移动排课片段的日志。

关键字段：

| 字段 | 说明 |
|---|---|
| `scheme_id` | 所属方案 |
| `item_id` | 被调整的排课明细 |
| `teaching_task_id` | 教学任务 |
| `from_time_slot_id` / `to_time_slot_id` | 调整前后时间 |
| `from_classroom_id` / `to_classroom_id` | 调整前后教室 |
| `reason` | 调整原因 |

### 2.4 `adjustment_request`

用途：正式课表发布后的调课申请。

关键字段：

| 字段 | 说明 |
|---|---|
| `assignment_id` | 原正式课表 ID |
| `teacher_id` | 申请教师 |
| `reason` | 调课原因 |
| `preferred_time_text` | 期望时间，自然语言 |
| `status` | `PENDING` / `APPROVED` / `REJECTED` |
| `review_note` | 审核意见 |

当前状态：审批通过 / 驳回会更新 `status`，并写入 `ml_feedback_event` 的调课审核事件。

## 3. 已有后端接入点

### 3.1 方案确认

接口：

```text
POST /api/allocation-schemes/{id}/confirm
```

代码位置：

- `server/src/main/java/com/yuy/eduflow/allocation/AllocationSchemeController.java`
- `server/src/main/java/com/yuy/eduflow/allocation/AllocationSchemeConfirmService.java`
- `server/src/main/java/com/yuy/eduflow/ml/MlFeedbackEventService.java`

现有行为：

```text
确认方案
  → 写入正式课表 course_assignment
  → 更新方案状态为 CONFIRMED
  → 其他候选方案置为 REJECTED
  → 写入 allocation_scheme_feedback
  → 写入 ml_feedback_event: SCHEME_CONFIRMED
```

画像含义：

- 被确认方案整体可视为弱正反馈。
- 方案内长期未被调整的 item 可视为弱正样本。
- 其他被拒绝方案暂时没有显式负反馈，需要谨慎使用。

### 3.2 人工移动排课片段

接口：

```text
PUT /api/allocation-schemes/{schemeId}/items/{itemId}
```

代码位置：

- `server/src/main/java/com/yuy/eduflow/allocation/AllocationSchemeController.java`
- `server/src/main/java/com/yuy/eduflow/allocation/AllocationItemService.java`
- `server/src/main/java/com/yuy/eduflow/ml/MlFeedbackEventService.java`

现有行为：

```text
移动 item
  → 更新 allocation_item 的 classroom/time_slot
  → 写入 allocation_item_adjustment_log
  → 重新检测方案冲突与画像软提示
  → 写入 ml_feedback_event: ITEM_MOVED
```

画像含义：

- `before_snapshot_json` 中的原安排可作为负向证据。
- `after_snapshot_json` 中的新安排可作为正向证据。
- 若只换教室不换时间，则主要影响教室类型偏好，不应误判为时间偏好。

### 3.3 人工好坏标注

接口：

```text
POST /api/allocation-schemes/{schemeId}/items/{itemId}/feedback
```

前端入口：方案详情页的“编辑排课片段”弹窗。

代码位置：

- `web/src/views/admin/AllocationView.vue`
- `server/src/main/java/com/yuy/eduflow/allocation/AllocationSchemeController.java`
- `server/src/main/java/com/yuy/eduflow/ml/MlFeedbackEventService.java`

现有行为：

```text
标为可参考 → ml_feedback_event: ITEM_MARKED_GOOD
标为不满意 → ml_feedback_event: ITEM_MARKED_BAD
```

画像含义：

- `ITEM_MARKED_GOOD` 是强正反馈。
- `ITEM_MARKED_BAD` 是强负反馈。
- 这类事件比“方案被确认”更适合直接进入教师画像证据。

### 3.4 调课申请审批

接口：

```text
POST /api/adjustment-requests/{id}/confirm
POST /api/adjustment-requests/{id}/reject
```

代码位置：

- `server/src/main/java/com/yuy/eduflow/adjustment/AdjustmentRequestController.java`
- `server/src/main/java/com/yuy/eduflow/adjustment/AdjustmentRequestService.java`

现有行为：

```text
审批通过 / 驳回
  → 更新 adjustment_request.status 与 review_note
  → 读取原 course_assignment 快照
  → 写入 ml_feedback_event: ADJUSTMENT_APPROVED / ADJUSTMENT_REJECTED
```

已补充事件类型：

```text
ADJUSTMENT_APPROVED
ADJUSTMENT_REJECTED
```

画像含义：

- `ADJUSTMENT_APPROVED`：原安排大概率不满足教师或业务偏好，是强负反馈。
- `preferred_time_text`：可通过 LLM 或规则解析为偏好证据。
- `ADJUSTMENT_REJECTED`：不能直接当正反馈，只能作为弱信号或审计事件。

## 6. 推荐实现方案

### 6.1 复用现有事件表

不新增 `teacher_profile_feedback_event` 表，先复用：

```text
ml_feedback_event
```

理由：

- 已有 schema。
- 已有 Mapper / Service。
- 已有事件摘要和训练导出接口。
- 方案确认、人工移动、人工标注已经接入。

### 6.2 补充调课事件写入

在 `AdjustmentRequestService.confirm()` 中补充：

```text
ADJUSTMENT_APPROVED
```

在 `AdjustmentRequestService.reject()` 中可选补充：

```text
ADJUSTMENT_REJECTED
```

需要写入：

- `teacher_id`
- `assignment_id`
- 原 `course_assignment` 快照
- `reason`
- `preferred_time_text`
- `review_note`

由于 `ml_feedback_event` 当前没有 `teacher_id` 和 `assignment_id` 字段，可以先放入 `context_snapshot_json`，暂不改表。

### 6.3 增加画像聚合服务

后端已新增聚合服务：

```text
TeacherProfileFeedbackAggregationService
```

当前聚合结果已挂到 `/api/ml/teacher-profiles/v3` 的教师画像对象上：

```text
feedback_profile
feedback_evidence_summary
feedback_confidence
```

MVP 当前只附加反馈画像证据，不覆盖 `final_profile`，避免反馈样本量不足时冲掉教师手动声明。

职责：

```text
读取 ml_feedback_event
  → 通过 teaching_task_id / assignment_id 反查教师
  → 解析 before / after / context 快照
  → 聚合偏好证据
  → 输出 profile evidence + confidence
```

第一版聚合规则：

| 事件 | 处理方式 | 权重 |
|---|---|---|
| `ITEM_MARKED_GOOD` | 当前 item 的时间/教室作为正向证据 | 强 |
| `ITEM_MARKED_BAD` | 当前 item 的时间/教室作为负向证据 | 强 |
| `ITEM_MOVED` | before 负向，after 正向 | 中 |
| `SCHEME_CONFIRMED` | 方案内 item 作为弱正向证据 | 弱 |
| `ADJUSTMENT_APPROVED` | 原 assignment 作为负向，preferred text 作为声明证据 | 强 |
| `ADJUSTMENT_REJECTED` | 仅审计，默认不参与画像 | 弱 / 不参与 |

### 6.4 合并进 V3 教师画像

当前 V3 画像合并规则可以演进为：

```text
教师手动编辑
  > LLM 声明解析
  > 调课反馈 / 人工标注
  > 人工移动调整
  > 正式课表
  > 历史课表
```

MVP 阶段建议只新增：

```text
feedback_profile
feedback_evidence_summary
feedback_confidence
```

不要急着覆盖教师手动声明。

### 6.5 前端展示

在教师画像页增加三类信息：

- 反馈事件数量。
- 最近反馈事件。
- 由反馈推断出的偏好证据。

第一版可以只展示，不提供复杂编辑。

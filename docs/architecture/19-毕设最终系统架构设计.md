# 毕设最终系统架构设计

> 本文档定义 Edu-Flow-AI 毕业设计最终形态。它不是单点算法说明，而是从学校真实数据进入系统，到智能排课、人工反馈、教师画像演进、多角色课表导出的完整业务闭环。

---

## 1. 设计目标

Edu-Flow-AI 的最终目标不是“生成一张课表”，而是构建一个面向学校教务场景的智能排课平台：

```text
历史数据导入
  → 资源建模
  → 教师画像生成
  → 智能排课
  → 人工调整 / 反馈
  → 画像更新 + 模型训练
  → 多角色导出
```

系统完成标准可以拆成三大业务能力：

1. **导入**：能够从历史课表、基础数据、教务表格中解析出真实课表、班级、教师、教室、课程等资源，并支持多轮导入中的冲突对比与人工确认。
2. **排课**：能够将导入数据与系统内自行创建的教学任务合并，生成质量高、美观、无硬冲突的候选排课方案。
3. **多条件导出**：能够面向学生、教师、教务、教室管理者等不同角色，导出各自视角下清晰可用的课表。

核心创新点是 **教师画像驱动的反馈训练闭环**：系统从历史课表、正式课表、调课变动、教师手动填写、人工反馈中持续提取画像信号，并将其作为模型特征、软约束目标和训练样本的一部分，使后续排课逐步接近真实使用者偏好。

```text

  → 前端展示与冲突检测
```

## 3. 模块一：数据导入与冲突治理

### 3.1 目标

导入模块负责把学校已有的“非标准数据”转成系统可计算的数据资产。

输入来源包括：

- 历史真实课表
- 班级、专业、课程、教师、教室等基础资源表
- 已确认的正式课表
- 后续调课、停课、补课记录
- 教务手工维护的数据

输出结果包括：

- `semester`
- `class_group`
- `course`
- `teacher`
- `classroom`
- `teaching_task`
- `schedule_item`
- 历史排课样本
- 教师画像原始证据

### 3.2 多轮导入冲突处理

学校数据经常会被多次导入，且不同文件之间存在冲突。系统不应静默覆盖，而应提供对比治理机制：

```text
新导入数据
  → 字段标准化
  → 与现有资源匹配
  → 识别新增 / 更新 / 冲突 / 删除候选
  → 展示差异对比
  → 教务人工选择保留策略
  → 写入正式数据
```

典型冲突包括：

| 冲突类型 | 示例 | 处理方式 |
|---|---|---|
| 同名不同 ID | 两个文件中都有“张三”，但工号不同 | 提示人工合并或保留为不同教师 |
| 同 ID 不同属性 | 同一教室容量变化 | 展示旧值、新值，选择覆盖或保留 |
| 课程归属变化 | 课程所属专业或年级变化 | 生成变更记录，避免直接覆盖历史样本 |
| 历史课表冲突 | 同一教师同一时间出现两个安排 | 标记异常样本，不进入训练集或等待人工确认 |

### 3.3 与教师画像的关系

导入模块不仅构建基础资源，也为教师画像提供第一批证据：

```text
历史课表
  → 教师常用星期 / 常用节次 / 常用教室类型 / 日课时分布
  → 历史推断画像
```

## 4. 模块二：智能排课

### 4.1 排课输入

排课任务由两类数据共同组成：

1. **导入数据**：从历史课表和基础数据中解析出来的学校资源与历史规律。
2. **系统创建数据**：教务在系统内维护的新学期教学任务、课程安排、教师安排、教室资源和约束条件。

统一进入排课任务后，形成：

```text
allocation_task
  ├─ teaching_tasks
  ├─ teachers
  ├─ classrooms
  ├─ class_groups
  ├─ constraints
  └─ teacher_profiles
```

### 4.2 排课核心链路

当前推荐保留 V3 架构：

```text
Placement Model 负责“像真实课表一样推荐候选位置”
CP-SAT 负责“在全局范围内保证无硬冲突并优化软目标”
```

分工如下：

| 组件 | 职责 | 不负责 |
|---|---|---|
| Placement Model | 为每个教学任务预测 TopK 候选位置 | 不直接决定最终课表 |
| Task Plan Generator | 把候选位置扩展成可求解的排课模板 | 不做全局冲突判断 |
| CP-SAT Solver | 选择一组全局无冲突 task plans | 不理解自然语言偏好 |
| Java 后端 | 管理任务、方案、入库、接口、权限 | 不承担核心求解 |
| 前端 | 创建任务、查看方案、人工调整、导出 | 不直接生成算法结果 |

### 4.3 方案质量目标

最终候选方案需要同时满足：

- **硬约束无冲突**：教师、班级、教室、时间不可冲突。
- **资源合理**：教室容量、教室类型、校区等满足任务需求。
- **结构美观**：减少碎片化、减少过早/过晚课程、尽量紧凑。
- **教师满意度高**：尽量符合教师画像中的偏好与避让条件。
- **可解释**：能说明某个方案为什么较优、哪些教师满足度较低。
- **可调整**：教务可以人工修改，修改结果进入反馈闭环。

## 5. 模块三：多条件课表导出

### 5.1 目标

导出模块负责把同一份正式课表转换成不同角色能理解、能使用的视图。

不同角色关注点不同：

| 角色 | 关注内容 | 导出形式 |
|---|---|---|
| 学生 | 自己班级每周上什么课、在哪上 | 班级课表、学生视图 |
| 教师 | 自己每周何时何地上课 | 教师课表 |
| 教务 | 全校总表、冲突检查、方案归档 | 总课表、统计表、方案报告 |
| 教室管理者 | 每个教室何时被占用 | 教室占用表 |

### 5.2 导出维度

导出能力应支持按以下条件组合：

- 学期
- 排课任务
- 排课方案
- 班级
- 教师
- 教室
- 课程
- 周次
- 星期
- 节次

### 5.3 与反馈闭环的关系

导出不是流程终点。正式课表发布后，真实使用过程中的调课、人工修改和教师反馈会重新进入教师画像与训练样本链路：

```text
正式课表 / 导出课表
  → 使用过程中的调课、修改、反馈
  → 正负样本采集
  → 教师画像更新
  → Placement Model 重训
  → 下一轮排课质量提升
```

## 6. 创新点：教师画像驱动的反馈训练闭环

教师画像不是简单的展示字段，而是系统智能化的核心中间层。

### 6.1 画像来源

教师画像由多种来源融合生成：

| 来源 | 信号类型 | 示例 |
|---|---|---|
| 历史课表 | 隐式偏好 | 常上星期、常上节次、常用教室类型 |
| 正式课表 | 已接受安排 | 最终发布且长期未调整的安排 |
| 调课变动 | 负反馈或偏好修正 | 某教师频繁调走早八或晚课 |
| 教师手动填写 | 显式声明 | 避开第一节、偏好连续排课、不可用时间 |
| 教务人工调整 | 高价值反馈 | 教务把某课程从 A 时间移到 B 时间 |
| 方案选择行为 | 方案级偏好 | 教务最终选择满足度更高的方案 |

### 6.2 画像结构

画像应保留“来源”和“可信度”，避免把所有信号混成一团：

```json
{
  "teacher_id": "T001",
  "final_profile": {
    "avoid_early_period": true,
    "prefer_compact_schedule": true,
    "preferred_weekdays": [1, 3, 5],
    "max_daily_lessons": 4
  },
  "evidence": {
    "historical_schedule": {},
    "official_schedule": {},
    "adjustment_feedback": {},
    "declared_profile": {}
  },
  "confidence": {
    "avoid_early_period": 0.82,
    "prefer_compact_schedule": 0.74
  }
}
```

MVP 阶段可以先采用固定优先级：

```text
教师手动编辑 > LLM 声明解析 > 调课反馈 > 正式课表 > 历史课表
```

### 6.3 画像进入排课模型

教师画像需要进入两个位置：

#### 6.3.1 进入 Placement Model 特征

将画像字段转为模型特征，使模型学习“某类教师更可能接受什么样的安排”：

```text
task 特征
  + teacher_profile 特征
  + historical placement 特征
  → Placement Model
  → TopK 候选位置
```

可加入的特征包括：

- 是否避开早课
- 是否避开晚课
- 是否偏好紧凑排课
- 偏好星期分布
- 偏好节次分布
- 最大单日课时
- 常用教室类型
- 调课负反馈计数
- 人工调整接受率

#### 6.3.2 进入 CP-SAT 软目标

CP-SAT 不直接训练，但可以把画像转成软目标权重：

```text
objective =
  教室匹配分
  + 时间结构分
  + 教师画像满足度分
  + 方案多样性分
  - 违背偏好惩罚
```

这样可以做到：

- 硬约束仍然绝对优先。
- 教师偏好作为软目标参与优化。
- 方案输出时能解释哪些偏好被满足或牺牲。

### 6.4 正负样本闭环

系统需要把人的行为变成训练信号：

| 行为 | 样本含义 |
|---|---|
| 教务选择某个候选方案 | 该方案整体为正样本 |
| 教务放弃某个候选方案 | 该方案相对为负样本 |
| 人工把课程从 A 调到 B | A 是负样本，B 是正样本 |
| 教师申请调课并被批准 | 原安排可能违背教师真实偏好 |
| 教师长期未调整某安排 | 该安排可作为弱正样本 |

最终形成闭环：

```text
排课结果
  → 人工选择 / 修改 / 调课 / 反馈
  → 反馈事件表
  → 教师画像更新
  → 训练样本生成
  → Placement Model 重训
  → 下一轮排课
```

## 8. 推荐落地阶段

### Phase 1：导入闭环补强

- 完善历史课表导入流程。
- 增加导入预览与字段映射。
- 增加多轮导入差异对比。
- 增加冲突确认与导入日志。

### Phase 2：教师画像反馈信号

- 接入调课申请、人工调整、方案选择行为。
- 设计反馈事件表。
- 将反馈事件聚合为教师画像证据。
- 在教师画像页展示来源与可信度。

### Phase 3：画像进入 CP-SAT

- 在 task plan 中计算教师画像满足度。
- 将画像满足度加入 CP-SAT objective。
- 输出方案时附带教师画像解释。
- 对比加入画像前后的满足度变化。

### Phase 4：画像进入模型训练

- 将教师画像字段加入训练样本。
- 引入人工调整产生的正负样本。
- 重训 Placement Model。
- 对比 hit@k、冲突率、满足度、人工调整次数。

### Phase 5：多角色导出

- 教师课表导出。
- 班级 / 学生课表导出。
- 教室占用表导出。
- 教务总表与方案报告导出。

## 9. 论文表述建议

可以将系统创新点概括为：

> 本系统提出一种融合历史排课数据、教师画像与反馈训练闭环的智能排课方法。系统利用 LightGBM Placement Model 从历史课表中学习教学任务的候选安排位置，再通过 OR-Tools CP-SAT 在全局硬约束下选择无冲突方案。同时，系统构建教师画像层，将历史课表、正式课表、调课记录、教师声明和人工调整反馈转化为结构化偏好特征，分别参与候选生成、软目标优化和模型再训练，从而提升课表方案的可用性、满意度与持续优化能力。

答辩时可以强调四点：

1. **不是让 LLM 直接生成课表**：LLM 只用于理解非结构化偏好，核心排课由 ML + CP-SAT 完成。
2. **不是单次排课工具**：系统包含导入、排课、反馈、训练、导出的完整闭环。
3. **不是只追求无冲突**：系统还考虑教师满意度、课表美观度和方案可解释性。
4. **不是静态规则系统**：教师画像和反馈样本会持续改进模型。
